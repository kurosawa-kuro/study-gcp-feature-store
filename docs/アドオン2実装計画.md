## 1. 目的・スコープ

BigQuery 上の複数の raw / master テーブル（検索ログ・PVログ・お気に入り/問い合わせログ・物件マスタ）から、**BigQuery 内の SQL だけで Feature Store 投入用の特徴量テーブルを生成する**。データ収集・結合・集計・欠損補完・期間集計・`feature_timestamp` 付与を検証する。

```
BigQuery raw / master tables
  ↓ BigQuery SQL（JOIN / 集計 / 欠損補完 / 期間集計 / feature_timestamp 付与）
BigQuery feature table（property_features_daily）
  ↓
Vertex AI Feature Store
```

**やらない（spec 対象外）**:
- 外部 DB 連携しない
- モデル学習しない
- **Dataform は使わない**（plain BQ SQL で行う = 本 project の no-Dataform 方針を維持）

既存 `seed`（固定 5 件を直接投入する quick 路線）は**残し**、本アドオンは `seed-raw` → `build-features` の現実路線を**併存**で追加する。

## 2. アーキテクチャ / データフロー

```
raw dataset (新規)
  property_master   物件マスタ
  search_log        検索結果に出た = impression
  pv_log            物件詳細PV = click 相当
  favorite_log      お気に入り / 問い合わせ
        ↓ seed-raw   (app/seed_raw.py : CREATE OR REPLACE TABLE + サンプル投入, 冪等)
  BigQuery SQL (app/sql/build_features.sql)
        - 28日 window 期間集計
        - LEFT JOIN（行動ゼロ物件も全件）
        - SAFE_DIVIDE / COALESCE で欠損補完
        - feature_timestamp 付与
        ↓ build-features (app/build_features.py : 当日分 DELETE→INSERT, 冪等)
  feature_mart.property_features_daily   ← schema は既存と完全一致
        ↓ make sync
  Vertex AI Feature Store（Feature Group / View は無変更）
```

**重要**: 出力 `property_features_daily` の schema を既存と一致させるため、Feature Group / Feature / Feature View は**一切変更不要**。アドオン2 は「seed の中身を固定値 → raw 由来の集計値に差し替える」だけで Feature Store 側に波及しない。

## 3. raw テーブル設計（不動産ドメイン）

新規 dataset `raw`（BQ raw → feature mart の二層構造を学ぶため feature_mart と分離）。

| テーブル | スキーマ | 役割 |
|---|---|---|
| `property_master` | `property_id STRING REQUIRED`, `rent INT64`, `walk_min INT64`, `age_years INT64`, `area_m2 FLOAT64`, `layout STRING`, `city STRING`, `ward STRING` | 物件マスタ。rent/walk_min/age_years/area_m2 の源 |
| `search_log` | `search_id STRING`, `property_id STRING REQUIRED`, `query STRING`, `rank INT64`, `timestamp TIMESTAMP REQUIRED` | 検索結果に物件が表示された = impression（ctr 分母） |
| `pv_log` | `property_id STRING REQUIRED`, `user_id STRING`, `timestamp TIMESTAMP REQUIRED` | 物件詳細ページ閲覧 = click 相当（ctr 分子） |
| `favorite_log` | `property_id STRING REQUIRED`, `user_id STRING`, `action STRING REQUIRED`(`favorite`\|`inquiry`), `timestamp TIMESTAMP REQUIRED` | お気に入り（fav_rate 分子）/ 問い合わせ（inquiry_rate 分子） |

ログ系は `timestamp` で DAY partition + `property_id` clustering を付ける（参照実装の log テーブル準拠）。

## 4. 特徴量生成 SQL（`app/sql/build_features.sql`）

参照 `study-gcp-search-mlops-gke/.../property_features_daily.sqlx` を **plain BQ SQL** に移植（`${ref(...)}` → 実テーブル名、`{project}` はアプリ側で format）。

```sql
DECLARE event_date DATE DEFAULT CURRENT_DATE("Asia/Tokyo");

DELETE FROM `{project}.feature_mart.property_features_daily`
WHERE event_date = CURRENT_DATE("Asia/Tokyo");

INSERT INTO `{project}.feature_mart.property_features_daily`
  (event_date, feature_timestamp, property_id, rent, walk_min, age_years, area_m2,
   ctr, fav_rate, inquiry_rate, popularity_score)
WITH window_bounds AS (
  SELECT TIMESTAMP(DATE_SUB(CURRENT_DATE("Asia/Tokyo"), INTERVAL 28 DAY)) AS window_start
),
impressions AS (
  SELECT property_id, COUNT(*) AS impression_count
  FROM `{project}.raw.search_log`, window_bounds
  WHERE timestamp >= window_bounds.window_start
  GROUP BY property_id
),
pv AS (
  SELECT property_id, COUNT(*) AS pv_count
  FROM `{project}.raw.pv_log`, window_bounds
  WHERE timestamp >= window_bounds.window_start
  GROUP BY property_id
),
acts AS (
  SELECT
    property_id,
    COUNTIF(action = "favorite") AS favorite_count,
    COUNTIF(action = "inquiry")  AS inquiry_count
  FROM `{project}.raw.favorite_log`, window_bounds
  WHERE timestamp >= window_bounds.window_start
  GROUP BY property_id
)
SELECT
  CURRENT_DATE("Asia/Tokyo") AS event_date,
  TIMESTAMP(CURRENT_DATE("Asia/Tokyo")) AS feature_timestamp,
  m.property_id,
  m.rent, m.walk_min, m.age_years, m.area_m2,
  SAFE_DIVIDE(pv.pv_count,        i.impression_count) AS ctr,
  SAFE_DIVIDE(a.favorite_count,   i.impression_count) AS fav_rate,
  SAFE_DIVIDE(a.inquiry_count,    i.impression_count) AS inquiry_rate,
  ( 0.4 * COALESCE(SAFE_DIVIDE(pv.pv_count,      i.impression_count), 0)
  + 0.2 * COALESCE(SAFE_DIVIDE(a.favorite_count, i.impression_count), 0)
  + 0.2 * COALESCE(SAFE_DIVIDE(a.inquiry_count,  i.impression_count), 0)
  ) AS popularity_score
FROM `{project}.raw.property_master` m
LEFT JOIN impressions i  USING (property_id)
LEFT JOIN pv             USING (property_id)
LEFT JOIN acts a         USING (property_id);
```

ポイント:
- **期間集計**: 28 日 window（`window_start` 以降のログのみ）
- **欠損補完**: `SAFE_DIVIDE`（impression=0 → NULL でゼロ除算回避）、`LEFT JOIN`（行動ゼロ物件も全件出す）、`popularity_score` は `COALESCE(...,0)`
- **feature_timestamp 付与**: `TIMESTAMP(event_date)`（Feature Group の feature-time 列要件）
- **schema 一致**: 列順・型を既存 `property_features_daily` に完全一致（INT64/FLOAT64）

## 5. アプリ実装

### `app/seed_raw.py`（新規）
4 raw テーブルを `CREATE OR REPLACE TABLE ... AS SELECT * FROM UNNEST([STRUCT<...>(...), ...])` で投入（参照 `seed_minimal.py` の properties_cleaned パターン）。
- `property_master`: p001〜p005（既存 seed と同じ basics）
- `search_log` / `pv_log` / `favorite_log`: **物件ごとに件数を変える**サンプル（例: p001 は impression 100/pv 5/fav 10/inquiry 2、p003 は impression 80/pv 6/fav 12/inquiry 3 …）。これで ctr/fav_rate/inquiry_rate が物件間で差が出て、集計が効いていることを目視確認できる。`timestamp` は直近数日に散らす。
- 冪等: `CREATE OR REPLACE` なので再実行で再生成。

### `app/build_features.py`（新規）
`app/sql/build_features.sql` を読み込み、`{project}` を format して `bigquery.Client(project).query(sql).result()` で実行。multi-statement（DECLARE/DELETE/INSERT）を 1 query で投げる。

### `app/main.py`（変更）
dispatch に `seed-raw` / `build-features` を追加（アドオン1 の `export` と合わせ dispatch table 化）:
```python
COMMANDS = {
    "seed": seed.run, "sync": sync.run,
    "seed-raw": seed_raw.run, "build-features": build_features.run,
    # "export": export.run,  # アドオン1
}
```

既存 `seed`（固定 5 件直接投入）は削除しない。
